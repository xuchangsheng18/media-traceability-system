# T024 worker隔离联调与剩余条件

2026-10-22续批，承接[非算法工程计划](non-algorithm-fast-delivery-plan-20261028.md)和[上传前端首批](business-upload-first-batch.md)。本批仅推进T024“实现分片合并与完整哈希”的隔离消费及故障子范围；准确命令、源码摘要和结果见[专项回执](../00-project/validation/t024-worker-isolated-integration-report.json)。

## 本批实现

`backend/business_app/uploads/messaging.py`在调用worker及确认消息前，比较消息中的上传、单位、案件、发起人四项绑定。任何不匹配或非对象消息均抛出既有`UPLOAD_EVENT_BINDING_INVALID`，不调用worker、不ACK。匹配消息沿用现有事件Schema、数据库outbox原文、来源版本和事务末授权检查，worker返回后才ACK。未增加HTTP接口、数据库迁移、队列名称或公共事件字段。

现有消息泵按指定上传工作，但队列按案件命名。它原来可能消费同案件内其他上传的消息；本批修复越过目标的处理，尚未提供多上传公平调度。其他上传位于队头时，当前选定上传会被拒绝并退出；原消息保留，由正确目标再次消费。本批不跳过、不丢弃、不确认其他上传的消息，也不将这一拒绝机制称为可用的常驻调度器。

## 隔离组合和实测范围

使用现有Linux Miniforge py310、真实RabbitMQ、随机PostgreSQL16测试库和实际文件对象存储。FastAPI测试客户端创建上传和完成回执；随后以`sys.executable`启动全新Python子进程，重新建立数据库和对象存储连接并调用实际消费代码。子进程只获得随机隔离库的受限运行角色凭据；临时配置权限0600，结束后删除。测试清理仅针对该次随机案件队列，保留公共exchange和其他队列。

| 场景 | 具体断言及边界 |
| --- | --- |
| 正常及重复 | 原完成请求重放保持同一202回执；同一持久化事件再次入真实队列后，不增加第二项资产或合并对象。 |
| 同案件不同上传 | A消费目标遇到B消息时拒绝，无资产副作用，消息仍待消费；B目标随后完成，A会话保持原状态。未证明多消费者公平或持续进展。 |
| 物理分片缺失 | 实际删除隔离对象文件后消费，状态REJECTED、无资产、无合并对象，已处理的拒绝消息被确认。 |
| 完整摘要不符 | 隔离会话的完整摘要与实际字节不符，状态REJECTED、无资产；未改动正式数据。 |
| 提交后、ACK前退出 | 在实际Kombu ACK边界令子进程退出73；数据库已COMPLETED，TCP断开后RabbitMQ重新投递；新进程消费后仍仅一项资产。不是任意崩溃点或整机恢复证明。 |
| 用户/案件关系撤销 | 发布后撤销，子进程启动时被数据库范围检查拒绝，原消息保持待消费；不是消费中途撤销测试。 |
| 来源撤销 | 发布后撤销来源，实际worker回调拒绝，不产生资产，消息未被确认。 |

独立子进程的权威及工作委托为明确标注的自建测试夹具，按当前RLS上下文读取合成目录/来源事实。测试发布器向真实RabbitMQ发送数据库已记录事件，用于分离发布和消费、重复投递；它不等于新增了可部署的生产发布器。现有生产发布确认、outbox提交失败及工作授权撤销的证据沿用相邻既有测试。本批不是浏览器到正式身份提供者的业务E2E。

## 执行和完成口径

针对性命令包含`test_upload_delivery_binding.py`、`test_upload_worker_process.py`、`test_upload_validation.py`、`test_uploads.py`和`test_t014_work.py`；实际运行目录与完整回归、失败探针、lint、格式及类型结果由专项回执绑定，不能从旧报告推断通过。绑定修复前12项新边界测试失败，修复后针对性68项通过；第一轮进程测试暴露的RLS上下文缺失已修复，未绕过RLS或降低断言。

初次完整回归949项出现6项失败、143项错误，原验证器仅保留汇总，未保留原错误堆栈。复查发现既有`control_context`夹具通过`prepared_upload`进入客户端上下文，结束时却只普通关闭HTTPX，遗漏Starlette lifespan及AnyIO portal退出。新增`test_client_lifecycle.py`实际复现“结束后portal仍可调用”，将清理改为匹配的`__exit__`后通过；最终worker8项及失败探针也通过。这个可复现泄漏不能直接证明原149项失败/错误的全部原因。

后续全量重跑附加私有、仅观察的pytest诊断：记录文件描述符/线程数量、异常类型和SQLSTATE，不输出异常消息、凭据或原始堆栈，不改断言、资源上限或原门禁。准确最终结果及源码差异以专项回执为准；进行中不登记全量通过。

第二次本机全量在原1800秒边界内未完成，验证器返回`BLOCKED_OR_FAIL`及0项汇总；诊断抽样到800个已执行call、无失败事件，末次正常退出后1个线程、15个文件描述符。这不能当950项通过。原失败节点的专项复测及精确提交的托管CI分别记录，最终托管结果以专项回执为准，原本机未完成记录继续保留。

最终源码下，首轮148个失败节点与新增生命周期回归合计149项通过，失败探针按预期返回非零；类型检查249个源文件、lint及格式检查通过。149项包含本批8项独立worker进程用例，不能累加成新的独立场景数。最终生命周期回归为满足静态类型检查，使用`getattr`取得同一个pytest包装前函数；专项回执对本机全量快照与最终源码的这一处测试反射差异进行了精确核对。
