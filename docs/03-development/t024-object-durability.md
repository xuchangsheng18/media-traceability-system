# T024 Linux文件对象的落盘持久性补齐

2026-10-22接续[快速交付计划](non-algorithm-fast-delivery-plan-20261028.md)第4项及[worker隔离联调](t024-worker-isolated-integration.md)。本批修复文件对象返回成功引用之前的目录同步缺口；精确源码、命令、结果和同步状态见[专项回执](../00-project/validation/t024-object-durability-report.json)。只覆盖当前Linux/Miniforge py310研发文件存储，不代表正式对象存储或整任务验收。

## 问题与实现

原`FileObjectStore.put_part`写入并同步文件后直接返回。Linux的文件`fsync`不保证包含它的目录项已经持久化，目录描述符还需要单独同步，依据[Linux man-pages fsync(2)](https://man7.org/linux/man-pages/man2/fsync.2.html)。因此，仅文件同步不能作为数据库发布该文件路径的充分屏障。

现有调用顺序保持：文件对象存储返回后，分片服务才登记`upload_part`和`object_version`；合并worker返回存储结果后，才登记合并对象、内容和资产。此次在返回之前增加屏障，未改HTTP、事件、数据库或权限契约：

1. 写文件、flush、同步文件描述符。
2. 同步新对象目录，确认文件名的目录项。
3. 同步对象根目录，确认新对象目录名的目录项。
4. 全部成功后返回`StoredObject`，调用者再按原事务、版本和授权检查发布引用。

目录以`O_DIRECTORY | O_NOFOLLOW`和只读描述符打开；同步成功或失败均关闭描述符。缺少目录标志时明确报`PRIVATE_OBJECT_DURABILITY_UNSUPPORTED`，不会跳过屏障返回成功。该限制没有被描述成Windows原生开发已支持；Windows继续作为远程入口。

## 新建对象根目录与重试

初始化先找到最近的既有目录，确认它及其父目录；随后逐级创建缺失目录，每一级同步自身及父目录后，才创建下一级。这样不再依赖`mkdir(parents=True)`一次创建多级后只同步最末目录。

若上一次初始化创建目录后同步失败，下一次将它视为既有锚点，重新同步锚点及父目录，再继续创建后代。目录同步失败则初始化失败，不返回可用存储。既有文件系统、挂载和锚点以上目录树的建立与恢复仍属于运行环境条件；本批不是对所有祖先目录、硬件写缓存或远端存储的持久性认证。

## 故障行为与实测

| 场景 | 实际检查 |
| --- | --- |
| 正常写入 | 使用真实临时文件，观察并实际执行文件→对象目录→根目录的同步；返回的固定版本可读、摘要匹配。 |
| 对象目录/根目录同步失败 | 注入`EIO`，不返回`StoredObject`；描述符关闭，既有侧车机制记录实际保留字节的大小和SHA-256，不删除文件。 |
| 根目录多级创建 | 观察每一级创建和同步的先后关系；初始化失败后重试，重新同步既有锚点。 |
| 不支持的运行时 | 缺少目录打开能力时失败，不把跳过同步当成功。 |
| 分片落盘失败 | 在真实随机PostgreSQL隔离库核对无分片、对象或分片幂等回执；恢复后同一请求可重试成功。 |
| 合并落盘失败 | 不发布资产或合并对象引用，会话保持VALIDATING；恢复后相同持久化事件可重试，最终仅一项资产。 |

新增回归先在未修复实现上出现9项失败，再由修复后的同一断言验证。相邻上传、worker、权限范围及原有部分写入故障测试另跑；准确最终数量以专项回执为准，不能把重叠测试相加当独立业务场景。

故障注入仅验证系统调用顺序、拒绝传播和数据库引用边界，**没有执行真实断电或整机崩溃恢复**。既有`.orphan.json`是尽力写入的排查材料；即使本轮可读取，也没有据此证明侧车本身已持久化，更不能把无侧车文件认定为可删除。
