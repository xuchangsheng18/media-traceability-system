## 3. 原生服务结构

使用systemd系统单元管理持久服务，应用调试可由指定用户在同一原生环境启动，但必须与受托管实例使用不同端口和数据目录。用户级服务不作为默认持久方案；缺少管理员初始化时只做预检和隔离验证。

| 服务 | 原生方式 | 数据与权限边界 |
| --- | --- | --- |
| PoC PostgreSQL | PostgreSQL16独立实例 | 独立数据目录、账号及连接配置；不覆盖已运行的业务库 |
| 业务研发PostgreSQL | 复用已验证16系列工具，单独systemd单元 | 先核对现有数据库/角色/迁移版本；测试库与长期开发库分列；不得删除其他实例 |
| RabbitMQ | 原生RabbitMQ及经官方矩阵验证的Erlang | 独立节点名、vhost、数据与cookie；保留权限及消息语义 |
| SeaweedFS | 官方Linux原生二进制 | 迁移volume数据、filer元数据及S3配置；不能只复制对象字节 |
| API、worker、CPU推理 | 指定py310，分别systemd单元 | 复用代码和运行锁；私密环境文件分离；推理权重/实验清单保留摘要 |
| Web | 已构建Vue静态资源及原生Nginx | 固定制品摘要；调试用Vite回环端口；远程访问通过SSH |
| Keycloak | 原生发行包及受支持Java | 保留既有realm、客户端策略及TLS；不用start-dev，管理员交接仍待落实 |
| 身份PostgreSQL | 独立PostgreSQL16实例 | 与业务库不同数据目录、登录角色和TLS材料，不做跨库复用 |
| 身份HTTPS网关 | 独立Nginx进程/单元 | LAN18443和回环18444边界保持；证书验证和公共admin拒绝保持 |

实际单元数量由服务与数据库实例清单生成，不用“十个容器”推定所有测试服务均已纳管。已有原生业务PostgreSQL是额外实例，不能遗漏。

## 6. 数据迁移与恢复要求

### 6.1 迁移清单和一致性时点

先记录每个项目实例、数据路径/卷、版本、端口、所有者、数据库、迁移号、对象数量/摘要、队列类型/消息计数、模型及身份信息的脱敏汇总。测试/长期研发/历史数据分列，不从容器名称推断归属。没有全量清单和可恢复备份不得切换。

切换顺序为：暂停新的上传/任务创建和登录等会改变状态的入口 → 停止新消息发布 → 等待已承诺任务完成或建立受控检查点 → 记录队列、outbox和数据库一致性水位 → 最终备份。数据库、对象和队列分别成功导出并不自动构成一致的业务快照。

### 6.2 PostgreSQL（PoC、业务、身份分别执行）

使用经锁定的PG16客户端执行逻辑归档；备份数据库、角色/权限及必要实例配置，分别记录恢复范围。`pg_dump`不含全局角色，角色与授权需单独纳入受控备份；不直接将Alpine数据目录搬到Ubuntu运行。

先恢复至新数据目录/新端口，核对Schema、表/约束/序列、RLS、角色权限、迁移版本、关键计数和业务历史身份。备份输出流式加密或写入私密加密介质；SQL/角色导出不得进仓库。缺少适用公钥/保管人时阻止正式备份交付，测试临时密钥不能当长期恢复能力。

依据：[PostgreSQL16 pg_dump](https://www.postgresql.org/docs/16/app-pgdump.html)。

### 6.3 RabbitMQ

Definitions仅包含用户、vhost、队列、交换机和绑定等元数据，不能替代消息备份。先核对队列类型和源节点名：有在途消息时必须选择“完成停写后排空并对账”，或验证原节点名兼容的停机消息恢复；未完成选择和演练时阻止切换。

默认采用停写、任务完成/检查点、队列排空与数据库outbox对账后导入definitions并逐条核验。不能清空队列来伪造排空，不对尚未证明幂等的任务直接重新发布；每个未确认消息必须有业务处置记录。

依据：[RabbitMQ备份恢复](https://www.rabbitmq.com/docs/backup)、[Erlang兼容矩阵](https://www.rabbitmq.com/docs/which-erlang)。

### 6.4 SeaweedFS及文件对象

一致性停写后同时迁移filer元数据、volume数据和S3权限配置；核对源filer后端类型，不能假定它一定在SQL或内嵌数据库。保持bucket、key、版本/保留属性及模型引用路径的有效映射。

逐对象记录源/目标数量、长度、内容SHA256和必要元数据；不能把S3 ETag一律当SHA256。对数据库引用对象与实际对象双向对账，发现缺失/多余/摘要错误时阻止发布业务入口。

依据：[SeaweedFS数据备份](https://github.com/seaweedfs/seaweedfs/wiki/Data-Backup)。

### 6.5 身份、配置和模型

身份库使用独立逻辑备份；realm导出不能替代完整数据库、签名状态与私密配置恢复。证书链、客户端secret和映射分别核验。切换前清理恢复的旧会话/提高适用not-before、轮换必要secret，实测旧凭据不能复活；未完成不得把身份切换视为通过。

模型权重、实验配置及代码按名称、版本和SHA256比对；本次保留已有合成CPU模型，不扩展成真实业务模型或训练验收。[Keycloak运行要求](https://www.keycloak.org/server/configuration-production)。

## 7. 资源、临时目录和服务安全

原生单元使用专属项目slice及每服务CPUQuota、MemoryHigh/MemoryMax、TasksMax，实际cgroup读值需与声明一致；不能只看配置文件。前述10.5核/10.5GiB仍是候选预算，未获得用户明确采用；现有身份服务3核/6GiB与业务原生数据库预算另列。需评估项目合计及其他应用负载，不能把宿主192线程理解为本项目独占。

临时目录采用有容量上限的独立tmpfs或受支持的文件系统配额；PrivateTmp本身不证明容量受限。每个服务先枚举临时写路径，再提出预算；数据库持久目录中的排序临时文件另用数据库约束验证。避免用容器/tmp测试冒充原生服务临时盘验收。

systemd单元明确User、UMask、工作目录、环境文件、Restart、启动/停止超时及日志保留。只读代码/二进制和显式可写路径分别配置；限制规则在隔离实例验证后启用，不能因限制失败而用root长期运行应用。

CPU/内存/临时盘/PID耗尽探针仅在隔离服务和新目录执行；证明相邻健康探针持续可用，实测不会写满宿主或现有项目卷。新单元经过systemd语法验证、重启持久化、退出SSH会话和启动顺序检查后才满足原生运维基础。

## 8. 切换和回退

并行恢复/新地址验证通过后，准备当前配置、备份摘要、服务版本和停止/启动顺序，给出实测恢复耗时。届时再确定切换窗口，不事先编造停机时长或RPO/RTO。

切换仅停止本项目占用旧端口的容器并启动对应原生单元；不删除容器、镜像或卷，不处理其他31容器。网络入口、只读查询、写入、队列、对象、模型及身份测试通过后才重新开放任务提交。

回退分两种：

1. **目标尚未接收新业务写入**：停原生目标、恢复旧私密配置/入口，启动保留的旧项目服务，验证既有数据及队列；原生目标保留用于排查。
2. **目标已接收新写入**：立即停写，先按数据库/outbox/对象/身份水位做差异恢复与对账。未经数据收敛不得直接启动旧数据副本，否则会丢失目标新增事实或重复处理消息。

必须保留至少一个已实际还原验证的加密备份及独立解密密钥保管路径。备份保留期限、清理责任和最终撤销旧容器须另获明确决定；本次不安排删除旧卷。
