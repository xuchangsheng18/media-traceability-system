# 从规划文档到可运行仓库

版本：0.1；整理日期：2026-10-12；状态：规划草案，NOT_FROZEN。

当前已有可启动CPU研发最小工程，见[实际运行手册](../10-deployment/development-runbook.md)；下表为完整业务的递进要求，不能以PoC代替全部交付。保留全部任务范围，不按编号机械并行。

| 步骤 | 对应重点 | 完成证据 |
| --- | --- | --- |
| 1 归档与版本管理 | T001、T010；阅读本包、确认目录，后续初始化Git | 文件摘要、差异、首批提交及目录检查 |
| 2 工程环境 | T002—T009；前后端、配置、日志、错误和最小CI | 干净环境安装、构建、健康检查、锁文件 |
| 3 基础闭环 | 权限、来源、上传、资产、任务和审核 | 合成素材完整流程与异常恢复 |
| 4 真实媒体与算法 | 预处理及图片同源先行，按依赖接OCR/ASR等 | 真实样例、权重版本、准确性及资源记录 |
| 5 扩展与验收 | 全部模块、联调、性能、安全、恢复及交接 | 逐任务证据与适用业务确认 |

首个闭环建议：测试身份登录 → 来源登记 → 上传合成素材 → 校验与摘要 → 持久化分析任务 → 显式模拟或真实结果 → 人工复核 → 测试报告。模拟结果必须标记，不能用来证明算法性能。正式报告权限未确定时仅验证测试流程。

开发某项前读取任务卡及其依赖、契约、权限和验收条件。文档中的output_refs_planned、runtime_test_file属于预期位置，只有真实实现并验证后才改变状态。发生接口变更时同步OpenAPI、Schema、SQL映射、任务和测试。

Git保存研发快照时先检查目录是否已有.git，预览待纳入文件，核验忽略规则；仓库托管地址及账号未知，不创建虚构origin。首批提交可以只含规划文档，不能打已批准基线标签。
