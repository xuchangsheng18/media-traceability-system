# Monorepo模式与拆分边界

2026-10-13；第三阶段研发实施候选，正式批准/冻结未完成。

当前仓库已经以Monorepo管理前端、后端、推理、共享契约、部署、脚本、测试和文档，本次沿用该结构。

| 维度 | Monorepo | 多仓库 |
| --- | --- | --- |
| 契约与版本 | 同一提交更新唯一OpenAPI/Schema和生成类型 | 需单独版本、制品发布和跨仓兼容验证 |
| 权限边界 | CODEOWNERS和目录评审不提供Git级不可读取隔离 | 适合需严格代码可见性隔离的独立团队 |
| CI效率 | 当前单CPU工作流可验证工程闭环，后续按目录影响优化 | 每仓独立CI，还需跨服务集成环境 |
| 训练/推理与大文件 | 代码共同管理，权重和素材继续外置 | 发布节奏独立，但模型契约、权重许可与数据来源仍必须关联 |
| 协作与拆分 | 当前小团队未确定，沿用结构可保留现有证据 | 需明确组织边界和发布責任，拆分会增加协调成本 |

当前选择仅为研发执行方案，正式审批待完成，见[ADR-013](../02-architecture/architecture-decisions/ADR-013-repository-structure.md)。以后只有存在实际权限/发布/规模理由及迁移计划时拆分，禁止复制第二套字段定义。data-pipeline/tools为预留代码边界，不移动原datasets、scripts或权重。
