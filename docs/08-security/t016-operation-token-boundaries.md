# T016 案件签发与内部消费安全边界

2026-10-21。开发负责人、指定复核人均为徐昌胜。适用当前 Linux／Miniforge py310／CPU、同一单位内部研发；Python候选继续暂缓。依据[批准实施计划](../03-development/t016-operation-token-implementation-plan.md)及[六角色隔离规则PR01／PR02／PR04](t014-six-role-rule-proposal.md)。本页说明当前代码边界，不登记测试、CI通过、正式权限采用或T016整任务验收。

## 1. 本批实现与未实现的边界

案件级签发沿用公共 `issueOperationToken`；内部消费由真实调用方传入其根Connection，不新增公共消费端点。首批唯一服务端映射为 `task + seal → sealEvidence`，且必须由显式规则端口给出规则版本和正TTL。未知、歧义或组织级用途继续拒绝，不按字符串purpose推断任意动作。

公共请求仍只有 `approval_id/object_id/object_version/purpose`，响应仍只有 `operation_token/expires_at/object_version`；单位、案件、actor和action从可信上下文与批准解析。客户端声明对象和用途必须与批准匹配，不允许客户端提交“已批准”、任意actor或案件扩大范围。

**真实 `sealEvidence` HTTP消费者尚未挂载。** 合成主体、合成动作授权及合成业务副作用只用于隔离内核验证；它们不代表真实封存、正式人员接管、共享授权或真实数据可用。现有审计导出的 `AuditExport` 不含operation_token字段，本批没有改变该公共契约或宣称既有导出已消费令牌。删除、解封、报告生成、组织模型发布及其他高风险消费者仍须在各自任务建立明确契约和业务前置。

## 2. 签发必须同时满足的条件

| 判定层 | 当前要求 |
| --- | --- |
| 主体与功能 | 有效认证主体，actor／issuer／subject绑定有效，具备当前 `operation.confirm` 资格；缺身份、权限或正式规则保持拒绝。 |
| 案件与对象 | 服务端从批准ID解析同单位案件，当前有效案件关系成立；请求对象ID／版本／purpose与批准一致。 |
| 六角色对象条件 | `CONFIRM_CASE` 同时要求同单位、案件关系、seal用途、当前申请主体、对象快照、来源、analysis用途与分类；未知必需事实不当作true。 |
| 批准与独立人员 | 当前批准状态为APPROVED；复用既有两名独立批准人、独立人员／职责事实和当前规则，不以确认按钮替代批准票。 |
| 当前快照 | 批准行版本、task对象版本、run/result、批准规则和最新结果仍匹配；来源及用途仍有效；同根读取当前单资产task实际来源的授权版本／状态／用途／截止／行版本，纯版本变更也使旧凭据失效。 |
| 规则与秘密 | 显式无歧义action及TTL、独立HMAC密钥可用；普通启动不安装合成成功提供方或默认secret。 |
| 根与提交 | 使用既有授权／范围根；提交前重验并保留最终T014栅栏。源码出现端口不等于正式提供方已采用。 |

接口范围与当前数据结构说明见[数据库扩展](../04-database/operation-token-extension.md)。规则和密钥缺失时503，非法绑定403，过期／已消费／状态冲突409；具体错误以[错误码表](../03-api/error-codes.md)及实际调用路径为准，案件越界继续遵循既有隐藏与拒绝语义。

## 3. 凭据不是授权替代物

完整凭据由域分离HMAC-SHA256和不可猜测令牌ID组成，绑定主体、单位、案件、批准及其版本、对象／用途／action、策略与规则版本、恢复代际、key_id、请求／主体摘要、幂等键和截止。数据库只保存凭据SHA-256及非秘密绑定元数据；摘要字符串、令牌ID或同purpose的另一动作都不能作为凭据接受。

响应使用 `Cache-Control: no-store`。同键合法重试只重建原凭据，不持久化完整响应，不新签第二条记录、不续期；每次仍检查当前事实。过期、消费、撤销、代际或密钥失效后不能借幂等重试恢复可用性。明文凭据不得进入数据库回执、日志、异常、审计详情、URL、Git或浏览器持久存储。公共报告不粘贴真实凭据、密钥或原始含连接信息的测试堆栈。

有效截止是“显式令牌TTL、批准截止、JWT截止、当前授权证据截止”的最小值。当前证据通常为5秒窗口，令牌因而可能只有不足5秒可用；审批1800秒和隔离规则60秒都不构成已采用的正式令牌TTL。当前实现不因新请求或重新认证延长既有截止，也不将事实刷新窗口泛化为所有业务作业超时。

HMAC密钥独立于游标、PoC和身份签名密钥，必须显式提供，材料不进入repr。本批仅接受**当前key_id与当前密钥材料**：轮换后旧记录立即拒绝，即使旧key仍保留且凭据未到期也不进入宽限接受路径。此严格边界不同于允许旧key继续消费的轮换窗口；后者需要独立方案。恢复代际改变后旧凭据拒绝，不能恢复旧库后手工改代际让其复活。

## 4. 同事务消费的调用契约

1. 调用方先取得自己的精确动作授权，并建立同一Database的变更根事务；`issueOperationToken` 的签发根不能当作 `sealEvidence` 执行根。
2. 调用方将该Connection及原对象／版本、批准ID、固定action和凭据传入内核。根的actor、单位、案件、对象和action须匹配；其他连接、其他Database实例或跨案件根必须在写入前拒绝。
3. 内核先无锁定位，再共享锁定批准／task，最后锁定令牌记录，核验完整HMAC及摘要、当前批准／人员／来源／对象、策略／规则、当前key、代际、截止及未消费状态，条件更新一次消费并在同连接写成功审计。
4. 调用方在同一根执行适用业务写入；内核不创建第二个消费事务，不自行提交。发生错误须使根回滚，不能吞掉应回滚的异常或提前commit。
5. 根提交前再次核验，并执行原权限栅栏。消费成功审计与业务写入一起提交或回滚；失败日志不能伪装成成功持久化审计。

当前提交前仍调用原批准快照重验。若业务动作本身提高被批准task的行版本，原快照检查会失败并使事务回滚；本批只能证明保留目标快照、追加独立产物或合成副作用的边界。真实封存消费者须明确批准原快照、业务产物以及最终状态的关系，再增加相应验收测试，不能仅凭一次合成UPDATE就声称任意业务更新可用。

## 5. 现有六角色与真实执行主体尚未闭合

PR01的案件核查人员 `case_investigator` 具有 `operation.confirm/CONFIRM_CASE`，而 `evidence.seal/SEAL` 授予业务审核员 `business_reviewer`。现行职责分离还限制同人在同对象上兼任冲突角色；不能为使测试通过而自动给核查人员封存权限或让审核员冒用申请主体。

本批凭据又绑定签发主体，消费时要求相同主体并重验 `operation.confirm`。因此，**现有规则不能直接推导出一个真实人员同时完成该签发与seal执行的合法链**。合成动作权限只是内核测试输入，不解决该业务决定。

后续真实消费者接入前，应明确以下事项并形成可审查规则：

- 谁是申请人、确认人、执行人，两名独立批准人与这些人员如何分离；
- 是否允许对精确案件／对象／版本／动作的执行委托，委托的期限、撤销与可信事实来源；
- 若确认主体与执行主体不同，凭据绑定、公共消费者及数据库怎样表达和核验双方，而不是只放松actor比较；
- 是否需要调整PR01的角色条件或职责冲突规则。任何调整须单独确认并同步规则、契约、代码和测试；本批不自动扩权。

## 6. 恢复、发布与证据口径

0011保留legacy为 `storage_version=0`，不补造旧action、密钥或批准，不消费旧记录。旧迁移字节及账本摘要继续保留；只向新建隔离数据库验证，不向共享库或现有预览库安装0011。完整0011目录为64表861列、operation_token为27列；源码同步不能当作数据库升级回执。

恢复旧库、轮换密钥、改变规则／代际、撤销批准／来源／人员关系、改变对象或run/result，均须按适用范围核验旧凭据拒绝。隔离模板／自建数据的恢复证据不能代替T013真实身份备份、本人接管或真实旧会话失效验证。

专项证据应列出实际源码摘要、迁移摘要、运行环境、执行命令、真实SQL／HTTP用例、竞争／回滚／恢复／秘密边界结果及未验证项；CI绑定确切提交和run，不用旧提交成功或排队状态替代本次通过。任务卡及分步导航只登记有证据的本批子范围，保留真实消费者、角色执行规则、正式共享采用和整任务验收事项。本页不预填任何成功数量。
