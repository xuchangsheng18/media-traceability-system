# 第一阶段与第二阶段的衔接

第一阶段24步回答“依据、需求、字段、任务和测试是什么”；第二阶段23步回答“采用什么技术、版本和环境，是否真实运行及可验证”。根170任务是具体研发清单，三套编号不能互换。

| 第一阶段输入 | 第二阶段消费方式 | 当前范围与限制 |
| --- | --- | --- |
| 来源、范围、术语、未决问题（1—10） | 环境/资源/非功能口径和技术比较（1—4） | 保持12模块与来源身份；未知业务规则、指标和资源不自动确定 |
| 流程、API、SQL/字典（11—13） | 前后端、数据库、存储、队列选型与验证（5—11） | 正式53操作/62表是输入；当前开发接口/5表只是最小工程子范围 |
| 模型、数据、媒体和安全要求（14—16） | 训练/推理/媒体/安全/部署（12—16） | 当前真实合成CPU模型与开发安全；真实业务模型、GPU、授权数据仍待落实 |
| 任务、测试、追踪与AGENTS（17—20） | 版本锁、规范、生成契约、最小工程和CI（17—21） | 保留170源任务状态；测试计划与实际运行报告分开；GitHub21门禁已有真实证据 |
| 审查、确认、修订、输入冻结（21—24） | 技术评审包及技术基线冻结（22—23） | 两阶段均需各自适用的有效确认，开发验证不自动升级为正式批准 |

依当前用户授权可继续可逆的工程建设和无敏感数据验证；并不因此宣称第一阶段已经正式冻结，亦不授权未确认的真实业务/证据动作。业务任务实施前读取任务卡、来源版本、执行依赖和适用未决项；正式冻结时登记实际责任人和决定，不使用空签字或虚构负责人。

当前状态请联合阅读[第一阶段24步](steps-and-deliverables.md)、[第二阶段23步](../../03-development/stage-two-readiness.md)、[第二阶段剩余条件](../../03-development/stage-two-gap-register.md)、[正式输入冻结检查](../baseline-1.0.md)。最新平台运行按[github-actions-report.json](../validation/github-actions-report.json)；历史评审中的“未上传”“未初始化”是先前时点，不能倒退当前实际工程状态。
