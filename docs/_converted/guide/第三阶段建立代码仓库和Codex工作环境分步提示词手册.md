# 一 使用说明

本手册与《第三阶段建立代码仓库和Codex工作环境实施指南》的16个实施步骤一一对应。每个步骤给出责任方式、必要输入、目标产物、可直接复制的提示词和验收标准。步骤1、3、4、6、14和16涉及人工决策、平台权限或最终批准，Codex只能辅助生成材料或在取得明确授权后执行。

建议每次独立任务先粘贴统一前置提示词，再附对应步骤提示词。方括号内容需要替换为实际路径、版本、批准记录或环境信息。

# 二 统一前置提示词

你正在参与“面向网络违法有害信息治理的短视频与图片智能识别溯源系统”建设。当前处于项目实施第三阶段：建立代码仓库和Codex工作环境。

工作依据：项目申报书、系统详细设计实现方案、Codex开发任务分解书、算法研发与训练数据集建设说明、已批准的Technical Baseline 1.0，以及仓库中的README、AGENTS.md、ADR、接口契约和工程规范。

总体要求：

1. 先检查现有仓库、技术基线和约束文件，再开展工作。

2. 不得自行决定代码仓库平台、权限范围、分支保护、安全等级和正式部署方式。

3. 未经明确授权，不得创建外部账号、推送远程仓库、创建合并请求、修改主分支、发布版本或删除文件。

4. 不得把真实账号、密码、Token、SSH私钥、数据库连接串和涉案数据写入代码、配置、日志或提示词。

5. 所有敏感配置必须使用环境变量、Secret或占位符。

6. 不得擅自改变Technical Baseline 1.0中已经批准的技术栈和版本。

7. 发现现有文件与技术基线冲突时，先输出冲突项、影响范围和处理建议，不直接覆盖。

8. 当前阶段只建立工程骨架、开发环境、质量工具和最小连通性验证，不开发完整业务功能。

9. 所有新增代码必须提供对应测试或自动化验证方法。

10. 完成任务后输出修改文件清单、执行命令、测试结果、未完成事项、风险及需要人工确认的内容。

安全要求：不接入真实公安业务数据；不使用真实违法有害信息样本；不将敏感文件提交到Git；日志不得输出凭据、个人信息和原始涉案素材；示例数据使用人工构造或公开无敏感数据。

如果完成任务所需信息不足，请停止有风险的操作，列出缺失信息和需要人工确认的事项。

必要输入：完整仓库骨架、开发环境和CI配置

目标产物：development-environment-validation-report.md

### 可直接复制的提示词

请执行第三阶段自动化验证，覆盖Git状态、目录和必需文件、Python/Node.js/Docker版本、GPU与CUDA、依赖安装、前后端和算法服务启动、前端调后端、后端调算法服务、格式/静态/类型检查、单元/契约/集成测试、敏感信息和依赖漏洞扫描、Docker Compose启动及CI语法检查。

每项标记通过、失败、未执行或不适用，不得把未执行写成通过。记录实际命令、环境、时间、结果、证据位置、失败原因、修复建议及是否阻塞下一阶段。

生成docs/03-development/development-environment-validation-report.md。

### 验收标准

□ 结果可复核

□ 状态严格区分

□ 失败项有修复建议

□ 明确冻结条件

## 步骤16 验收并冻结开发环境基线

责任方式：人工批准后Codex固化

必要输入：明确批准记录和完整验证报告

目标产物：Development Environment Baseline 1.0及变更文件

### 可直接复制的提示词

第三阶段评审已完成，批准记录位于【填写路径或会议纪要编号】。请先检查批准是否覆盖仓库平台、结构、分支、权限、前后端和算法环境、依赖版本、Docker、质量工具、CI、Runner、Secret、AGENTS.md和验证结果。

只有批准完整时，才更新Development Environment Baseline 1.0、将相关ADR改为已批准、固化锁文件与环境版本、更新README与AGENTS.md、生成基线清单、变更申请和回滚要求，并输出建议Git标签和发布说明。

未经明确授权，不推送远程、不创建标签、不发布版本。批准记录缺失或不完整时立即停止冻结，只输出缺失项和影响。

生成development-environment-baseline.md、development-environment-change-request.md和development-environment-acceptance-record.md。

### 验收标准

□ 冻结依据存在

□ 只冻结获批内容

□ 版本配置文档一致

□ 有变更和回滚机制

# 四 通用复核提示词

请对第三阶段“建立代码仓库和Codex工作环境”的全部成果进行一致性复核。

检查仓库结构与批准方案、技术版本与Technical Baseline 1.0、README/AGENTS.md与实际命令、本地与CI规则、OpenAPI/JSON Schema与骨架代码、Docker Compose服务/端口/环境变量的一致性；检查是否存在真实凭据、数据集、模型权重或涉案素材；检查分支保护、CODEOWNERS和审批规则；检查普通CI是否错误依赖GPU或大型模型；检查验证报告是否把未执行写成通过；检查是否引入未批准组件或大范围修改用户文件；检查是否形成Development Environment Baseline 1.0及变更回滚机制。

输出已通过项、不一致项、安全风险、阻塞项、建议修复顺序和需人工批准事项。不要自动修改已批准文件，先提供最小修复方案。

# 五 推荐执行顺序

人工先完成步骤1至4的决策、权限和账号准备。

Codex完成步骤5、7至13以及步骤15的设计、搭建和验证。

人工负责步骤6的评审、步骤14的平台配置和步骤16的验收冻结。

任何需要推送远程仓库、创建标签、发布版本或处理真实数据的操作，都必须单独取得授权。
