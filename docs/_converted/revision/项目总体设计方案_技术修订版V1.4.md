## 1 项目概述

本章说明项目背景、定位、建设原则与建设周期，明确系统为什么建、建在什么边界内。

### 1.1 建设背景

短视频、图片及其二次创作版本已成为网络违法有害信息和虚假叙事传播的重要载体。单一文件哈希、关键词匹配或单帧分类，无法稳定处理压缩、裁剪、镜像、字幕替换、音轨替换、变速、倒放、拼接、换脸和生成式编辑等复杂变形。

公安业务面临的实际问题不只是"有什么风险"，而是需要同时回答六个问题：

| 业务问题 | 对应技术能力 |
| --- | --- |
| 有什么风险 | 多模态风险识别 |
| 是否被修改 | 篡改与深度伪造检测 |
| 来自哪里 | 图片 / 视频同源检索 |
| 何时出现 | 首发候选分析 |
| 如何传播 | 传播路径分析 |
| 证据是什么 | 证据固化与报告 |


【源资料明确】现有单点技术无法支撑上述复合需求，需建设一套成体系的智能识别与溯源工具。

### 1.2 项目定位

【源资料明确】系统定位为在授权数据范围内运行的辅助核查原型：

不绕过平台访问控制获取数据；

不以模型输出替代行政认定、司法鉴定或执法决定；

首发、原创、违法性质及处置结论由授权人员审核确认；

所有核心结论必须绑定原始数据、分析过程、模型版本和人工审核记录。

源资料提出公安内网或授权专网私有化部署方向；当前用户只确认Linux服务器环境。具体网络类别、是否离线、数据准入和最终生产用途仍待Q-07、Q-28确认，不将172.16.58.179自动认定为已批准公安生产环境。

### 1.3 建设原则

| 原则 | 落实要求 |
| --- | --- |
| 合法授权 | 所有数据源登记权属、授权范围、用途和保存期限；不设计绕过访问控制的采集能力 |
| 证据优先 | 标签、相似度和自然语言说明不是证据本身；结论必须关联帧、时间段、区域、来源和模型版本 |
| 人机协同 | 高风险低置信、模型冲突、首发候选接近及新型篡改自动进入人工复核 |
| 多模型协同 | 分类、检测、取证、检索、图谱、规则和大模型按任务编排协同，避免单模型作最终判断 |
| 松耦合可替换 | 业务层只依赖能力契约，模型通过统一推理网关注册、路由、灰度和回滚 |
| 安全可审计 | 最小权限、数据分级、操作留痕、不可变证据、离线部署和全生命周期审计 |

## 2 建设目标与范围

本章界定系统的总体目标、建设范围与明确排除的非建设范围，并给出使用角色矩阵。

### 2.1 总体目标

【源资料明确】建设一套可私有化部署的短视频与图片智能识别溯源原型系统，形成如下闭环：

内容接入 → 风险识别 → 真实性取证 → 同源检索 → 片段溯源 → 首发候选 → 传播分析 → 人工复核 → 证据固化 → 报告生成

并完成事故灾害类谣言核查、违法有害视听内容识别、搬运篡改内容溯源等不少于 3 类场景验证。

### 2.2 系统范围

【源资料明确】

依法授权的公开内容、用户上传、历史材料和第三方系统数据接入；

图片和短视频预处理、多模态风险识别、篡改与深度伪造检测；

图片近重复检索、局部检索、视频片段级同源检索与多源拼接映射；

原始素材及首发候选排序、传播图谱、谣言证据核查；

任务审核、多人会审、证据固定、报告与工单、样本回流、模型运维。

### 2.3 非建设范围

【源资料明确】以下内容明确不在项目范围内：

不承诺对互联网全量实时覆盖，数据覆盖受授权来源与接入条件约束；

不以模型输出替代行政认定、司法鉴定或执法决定；

不实现未经授权的平台爬取、账号控制、规避验证码或访问限制；

不直接训练通用超大模型，重点进行任务适配、证据约束和可替换集成。

## 3 系统定位与设计原则

本章给出系统的五条设计导向与三类核心定位，是全文所有技术取舍的裁决依据。

### 3.1 五个设计导向

【源资料明确】本系统的设计围绕以下五条导向展开，它们直接约束后续每一项技术选择：

导向一 证据优先于判定。系统同时保存算法分析结果与可定位证据，展示帧、时间段、区域、匹配点和证据文本；算法结果标记为辅助判断，授权人员作审核确认，禁止隐藏证据只展示真假或违规按钮。

导向二 长分析任务异步执行。上传会话返回upload_id，文件完成校验后生成asset_id；分析任务创建接口校验通过后返回202和task_id，通过查询、SSE或批准回调取得进度。上传完成不等于分析完成，短查询接口可同步返回。

导向三：粗召回加精验证。 向量相似只产生候选。图片必须经几何验证、视频必须经时序对齐，才能确认同源。语义相似本身不构成同源证据。

导向四：大模型不直接定案。 大模型用于主张抽取、证据摘要和交互解释；其输出必须引用证据 ID，无证据句不得进入正式报告。

导向五：证据事件追加写。 分析和审核采用追加事件记录，已固化证据不覆盖，更正只能形成新版本。

## 4 总体架构设计

本章给出五层总体架构、三层推理链路与跨模块协作关系，是后续详细设计的骨架。

### 4.1 分层架构

【源资料明确】系统采用五层架构，纵向由安全运维体系覆盖全部层次：

| 层次 | 职责 |
| --- | --- |
| 业务应用层 | 任务、研判、审核和报告入口 |
| 能力服务层 | 任务编排、媒体处理、检索、图谱、证据和通知能力 |
| 智能算法层 | 通过推理网关暴露统一契约 |
| 数据资源层 | 按对象、关系、向量、全文和证据分别存储 |
| 基础设施层 | 计算、容器、消息、存储、监控和安全能力 |


分层要点：业务层只依赖能力契约，不直接调用具体模型；模型通过统一推理网关注册、路由、灰度和回滚。这一约束是"松耦合可替换"原则的落地方式，也是后续算法持续迭代而不影响业务系统的前提。

### 4.2 分层推理策略

【源资料明确】算法能力按三层次第投入，这是系统的性能骨架：

| 层级 | 触发范围 | 主要算法 | 目标 |
| --- | --- | --- | --- |
| 一级快速筛查 | 全部内容 | 轻量抽帧、 OCR 、 ASR 、 pHash 、固定目标检测、轻量分类 | 高吞吐召回与任务分流 |
| 二级深度核查 | 高风险或不确定内容 | 视频时空、多模态融合、图片 / 视频取证、开放词汇检测 | 提高精度并定位风险证据 |
| 三级取证溯源 | 需要来源或传播研判的任务 | 局部几何、序列对齐、首发排序、传播图和证据检索 | 形成可复核来源与传播证据 |


【建议】一级先分流，二级和三级按场景需求、规则及人工申请触发。OCR、ASR不对全部素材无条件执行完整重处理：无文本或无音轨时跳过，保留缺失模态标记；深度处理可在初筛返回后继续。轻量链路是否达标须按实际素材和硬件实测。

### 4.3 业务主流程

【源资料明确】

离线建库流程（面向授权数据底库建设）：

登记数据源、授权依据、采集或导入批次；

校验媒体格式并计算 SHA-256，完全重复内容关联既有对象；

生成标准化副本，完成镜头切分、关键帧、音轨、OCR、ASR 和元数据解析；

生成复制检测向量、语义向量、音频指纹和局部特征，并写入相应索引；

执行质量抽检、样本标注和内容簇聚合，生成可检索底库；

记录处理血缘、模型版本、失败原因和重试结果。

在线核查流程（面向具体案件任务）：

用户上传文件或提交授权 URL，系统完成鉴权、查毒、格式和大小校验；

创建上传会话并返回upload_id；校验、查毒通过后生成asset_id；再按场景创建分析任务返回task_id，记录文件哈希、来源及上传凭据。

运行一级快速筛查：轻量抽帧、OCR、ASR、感知哈希、固定目标检测；

根据规则进入二级深度分析：视频时空、多模态融合、图片或视频篡改检测；

需要来源核验时进入三级溯源：多路召回、几何验证、时序对齐、首发排序和传播图分析；

生成证据卡片和标记为待审核的算法分析结果；触发风险、冲突、不确定性或正式报告规则的任务进入人工复核。正式结论和报告按已确认制度审批，不允许以置信度高直接跳过正式审核。

复核通过后固化证据包、生成报告和处置工单，并将确认难例按审批流程回流。

### 4.4 任务状态机

【建议】分析任务与上传会话分别建模。下表为分析任务候选状态，输入必须为校验通过且当前用户有处理权限的媒体资产。业务退回、归档及取消权限等待Q-24确认，不能把本表认定为已批准流程。

| 状态 | 进入条件 | 允许转移 | 控制及记录 |
| --- | --- | --- | --- |
| CREATED | 绑定有效asset_id、场景及策略版本 | QUEUED、CANCELLED | 创建人及数据域；提交校验 |
| QUEUED | 调度请求持久化 | RUNNING、CANCELLED | 队列优先级、尝试号、策略版本 |
| RUNNING | 节点领取租约并执行DAG | WAIT_REVIEW、SUCCEEDED、FAILED、CANCELLED | 正式报告路径须复核；仅经批准非正式筛查可按策略完成 |
| WAIT_REVIEW | 形成复核快照 | REVIEWING、CANCELLED | 触发理由、结果与证据版本 |
| REVIEWING | 审核人经版本条件领取 | SUCCEEDED、RETURNED、WAIT_REVIEW | 记录意见；租约释放不丢审核历史 |
| RETURNED | 授权人员退回补充或重算 | WAIT_REVIEW、CLOSED；重算关联新版本QUEUED | 不直接进RUNNING；保留原意见及重算关联 |
| SUCCEEDED | 本分析版本按已确认策略完成 | ARCHIVED | 报告审批状态另管理；更正新建版本 |
| FAILED | 不可自动恢复或重试耗尽 | QUEUED、CLOSED | 可重试错误经授权重新入队；记录诊断 |
| CANCELLED | 取消检查点确认停止 | 终态 | 保留已生成证据；业务撤回另按审批 |
| CLOSED | 决定放弃本次处理 | 终态 | 关闭原因、人员、关联版本 |
| ARCHIVED | 满足已确认归档条件 | 终态 | 保留策略、归档号、校验记录 |


状态规则说明：

状态语义：SUCCEEDED表示本次分析版本按策略完成，不表示执法结论成立；ARCHIVED、CANCELLED、CLOSED为本次执行终止状态。FAILED是否重试以策略和错误类型决定，重试次数不由CI配置管理。

重试采用运行期任务策略，设置可重试错误、次数、退避、超时和人工诊断入口。每次尝试保存节点记录；重试回QUEUED并经调度执行，不从退回或失败状态直接跳入RUNNING。

退回路径分两类：仅补充解释或证据的，形成新补充记录并回WAIT_REVIEW；需要重新计算的，创建关联的新分析版本并回QUEUED。原版本和审核意见保留；最终路径及多轮复核规则由Q-24确认。

取消申请须校验申请人、数据范围、当前状态和执行版本；运行中由工作节点协作停止后记录终态。已产生的证据和审核记录保留；审核中取消涉及正式业务撤回时按确认的审批规则办理。

所有转移在数据库事务中校验状态与版本，记录前后状态、操作者、理由、request_id、时间及结果版本；并发领取、退回和确认使用条件更新，避免覆盖他人意见。

【待确认】Q-24决定正式退回、撤回、复核次数和归档流程；上表是避免直接调度和覆盖历史的工程候选。未确认前只能验证模拟流程，不能据此自动处理真实业务。

### 4.4.1 上传会话与任务恢复

【建议】上传会话独立使用upload_id，候选状态为CREATED、UPLOADING、VALIDATING、READY、REJECTED、FAILED、CANCELLED。仅READY对应可分析asset_id；校验拒绝不得进入算法队列。分片幂等键包括上传会话、分片号和校验值；合并锁及最终哈希防止重试生成多份原件。

分析提交的幂等键绑定单位、调用人、场景、asset_id和请求摘要；同键同摘要返回原task_id，同键不同摘要报冲突。跨案件重复文件可复用受控存储字节，但来源记录、授权和访问范围分别保存，查重接口不得泄露其他案件文件是否存在。

业务事务同时写任务及待发事件，由可恢复事件发送机制投递队列；消费者按event_id和节点幂等键去重。节点以租约、心跳和检查点记录运行，宕机后重新调度；结果先写受控对象再登记元数据，失败产生待清理孤儿对象并保留审计。达到重试上限进入人工诊断，不无限循环。

### 4.5 部署架构

【源资料明确】源设计提出五个逻辑分区。【待确认】实际网络分区、节点和访问清单需根据批准环境落实；单主机容器网络不能自动等同于已批准的安全隔离。

| 分区 | 服务 | 部署要求 |
| --- | --- | --- |
| 接入区 | API  网关、上传、第三方适配器 | 严格白名单；不直接访问核心数据库 |
| 应用区 | 业务后端、任务编排、审核、报告 | 无状态多副本；会话与状态外置 |
| 算法区 | 推理网关、 GPU  模型服务、媒体处理 | 现有CPU验证与未来授权GPU资源分别管理；当前GPU未确认 |

### 4.6 服务职责与降级

【建议】网关处理认证入口和限流；业务服务负责数据范围、任务与审核事务；媒体工作节点只生成派生对象；推理网关按能力与版本路由模型；检索服务返回经权限过滤的候选；证据服务管理引用、固化和报告版本。数据库保存权威状态，消息队列承载调度，Redis仅缓存。

按素材时长、分辨率、场景和模型成本设置队列及单位配额，队列满返回容量限制和可重试提示。重模型不可用时任务进入延期或明确的部分结果状态，列出未执行能力，不以轻量结果冒充深度核查或正式结论。超时、取消和部分失败在页面展示可追踪原因。

### 4.7 可靠调度与并发控制技术细则

官方机制：PostgreSQL的行锁可用于并发领取；SKIP LOCKED会跳过已锁行，适合队列消费而不适合要求完整结果的普通业务查询。Celery晚确认需要任务幂等，工作子进程丢失不等于普通异常重试；相关选项可能导致重复执行或重投循环。[R03—R05]

【建议】分析任务与待投递事件在同一SQL事务提交；outbox投递器按短事务领取事件、发送消息、登记发送结果。提交后至确认前宕机会重投，消费者以(task_id,run_version,node_key,input_digest)作幂等约束，在落库前校验租约及fencing_token，旧执行者不得覆盖新尝试。该outbox和fencing方案是项目工程设计，不是产品自动提供的跨存储事务。

Celery只是候选执行后端，业务状态以数据库记录为准；不得拿Celery SUCCESS代替人工审核通过。确定broker、可见性/确认机制、超时、max_retries、退避和队列容量后做故障PoC。长短任务分队列，预取与并发由实测设置；OOM、坏媒体和永久权限错误不得无限重投。

验收证据覆盖提交后投递失败、确认丢失、重复消费、租约过期、旧节点晚到、取消与重算竞争。T032—T039、T102负责实现及测试；正式退回/取消制度仍按Q-24。

#### 4.7.1 节点语义与任务完成条件

节点候选状态区分SUCCEEDED、SKIPPED、UNSUPPORTED、RETRYABLE_FAILED、FAILED、CANCELLED；SKIPPED必须有reason和missing_modality，不把失败冒充合法跳过。DAG边声明required/optional及接受的终态；无音轨/无语音/无字幕时可选边满足，必需能力失败则不能形成完整业务结果。

任务主状态保持§4.4候选枚举，增加能力完成矩阵、processing_completeness（COMPLETE/PARTIAL）、deferred_reason和report_eligibility字段表达延期/部分能力，字段以Schema评审为准。SUCCEEDED只代表该运行版本按策略完成；未执行能力明确显示，正式报告所需能力与复核条件不满足时不可发布。进度单调仅限同一run_version与已固定DAG。

取消记录cancel_requested、请求权限与版本；领取和最终提交均检查取消意图及fencing token，停止确认后进入CANCELLED。重试留attempt，重算新run_version；图片缺音频、某服务缺失、延期、取消竞争与晚到执行均须能终止并有诊断。

### 5.4 人工审核与报告审批

【建议】所有正式业务结论及正式报告由授权人员确认。重点复核入口包括高风险低置信、模型冲突、候选时间接近、跨模态矛盾、新型篡改和证据不足；具体阈值、单人或会审、双人审批范围待Q-18、Q-20确认。

审核流程为待领任务、按版本领取、核查原件与证据、填写理由、确认／驳回／补证／重算、必要会审、提交报告审批。确认和修改必须附证据；驳回保留算法原结果和理由；重算创建关联版本。审核员不得修改原始媒体或模型原始分数。多人同时操作以review_version条件更新，租约超时回待领取并保留记录。

样本回流与业务审核分开批准：人工确认结果不自动成为训练真值。数据管理员核查授权、保留与去重后，质检及必要仲裁形成数据集新版本；独立测试集不得进入难例回流。以上规则先以构造样例验证，真实业务适用性通过Q项审核。

### 6.7 核心算法实现路线

【源资料明确】详细设计第6章提出以下机制；具体模型组合和阈值保持候选。风险识别将视觉、目标、视频时序、OCR、ASR和音频事件映射统一时间轴，使用缺失模态掩码与时间位置编码融合，分别输出多标签风险、时间边界和跨模态一致性。一级保存轻量基线，二级分析矛盾与疑似片段，证据引用保留触发模态和区域。

图片取证区分原TruFor双线索接入与项目扩展的RGB/噪声/高频/编码元数据融合；扩展各分支有独立训练真值与消融。原始JPEG量化、EXIF和容器编码痕迹从受控原件读取，不由标准化副本反推；像素解码/缩放按模型验证版本执行。缺元数据或强转码记录限制；正常编辑痕迹不直接认定违法伪造。视频逐帧/跟踪、GOP、帧时序及音频连续性分别绑定输入来源与时间映射。

图片同源采用哈希、复制特征与语义特征多路召回，经授权范围过滤后用局部匹配与几何验证计算内点数、比例、覆盖及重投影误差。阈值在验证集确定；只命中相似语义而无几何支持时维持候选或不确定。全局近重复、局部裁剪和相似非同源分别评测，保留查询及来源匹配区域。

视频片段以带源时间戳的帧特征序列构造相似矩阵Mij=cos(qi,cj)，按来源视频聚合后用局部动态规划/DTW及音频支持对齐，惩罚过大时间跳变。正向、倒放、变速和多源拼接轨迹分别解析，输出查询区间、来源区间、方向、速度比和覆盖率；靠近边界细化抽帧并回映射源PTS。只靠单帧命中不能认定完整片段同源。

首发候选基于已定义整内容或指定片段范围的高可信簇；完全重复、整内容近重复、局部复制、来源包含与传播关系分别建模。多源拼接Q含A/B片段，不因A—Q—B连通把A和B合为整内容同源簇。排序结合可核验发布时间、发现时间、完整度/质量及水印等，输出Top-3、证据与覆盖；无可核验真值保持未知。显式转发与推断传播边分开，分数不自动转成事实路径。

证据核查从标题、OCR、ASR提取主体、行为、时间地点及结果等结构化主张，检索授权白名单证据并判支持、反驳、部分支持、相关但不支持及未知关系。摘要每个事实句绑定证据版本和支持关系；规则及语义核验后仍须人工审核。句子没有依据、引用已失效或证据不支持该句时拦截正式报告，而不是让生成模型自行补齐事实。

数据发布清单记录合格人工标注数、增强数、唯一原始素材数、内容组数、任务记录数和拒收数；分别统计不相加冒充独立素材。训练/验证/测试group_id交集必须为空；关联人物和事件隔离按任务核查。测试候选变化重新生成清单摘要和审核记录。撤销授权时按保留或冻结依据评估删除、索引失效及模型影响，不静默抹除审计。

### 7.7 分组划分与验收数据隔离技术细则

官方机制：GroupKFold按非重叠group构建交叉验证折，适用于防止同组跨折；它本身不提供最终验收测试集权限制度。[R17]

【建议】先按原始素材及同源衍生关系确定group_id，再生成训练、验证、独立测试清单；成对或多源拼接样本以来源组的连通关系检验交叉泄漏。人物、事件、平台、时间及生成器外推测试按各算法目标另建分层。不要把随机图片划分当成素材组划分。

对group交集、内容哈希、感知近重复和标签版本运行泄漏检查；泄漏或授权失效时冻结对应数据版本并记录重新划分影响。训练/难例挖掘/阈值调优仅用训练与验证集，独立测试集由验收角色受控执行；交叉验证成绩不替代独立测试。T110、T126—T127交付清单、权限及检查报告。

### 7.8 数据先行与评测用途

标注和基础划分先使用来源台账、原始素材、父子编辑血缘及人工已知关系建立group_id；不等待完整视频识别算法。T090聚类只补充分组/质量检查，Mock关系不作真值。多源组合的防泄漏分组可用共享素材连通关系保守隔离，但不把这种分组直接当业务首发内容簇。

T109/T110分前期规范/清单与后续集成校验；T092训练前有T164或同等首发簇清单、可核验参考来源及簇级切分。各类记录定义计数、合格性与人工质检；20万不是20万原始文件，增强、关系与人工记录分别统计。

训练、校准/阈值、开发回归与封存验收分别声明用途清单。校准样本与骨干训练隔离，必要时按group交叉拟合；多标签Sigmoid逐标签定义校准，不套用多类softmax归一化。isotonic regression译为等渗回归，固定ECE分箱、类别汇总/空箱处理及比较条件（R38）。独立测试在候选锁定后受控执行，记录次数与反馈，避免隐性调参。

### 8.5 接口设计约定

【源资料明确】核心接口约定：

基础路径 /api/v1；UTF-8；时间统一使用带时区 ISO 8601，内部统一保存 UTC；

认证与调用安全方案待技术基线确认。Authorization及request_id按接口规范使用；服务间或需防重放的敏感接口按方案增加时间戳、nonce及签名，定义规范化、允许时钟偏差、nonce保存和密钥轮换，避免把每个浏览器请求机械要求为自定义签名。

大文件分片上传；分析接口异步返回 202；重复提交通过 Idempotency-Key 实现幂等；

分页采用 cursor；错误返回 code、message、request_id 和可安全公开的 details；

对象ID采用约定的唯一标识；UUIDv7具有时间排序特征，不能据此宣称不可推断，也不能用ID隐蔽性替代授权。每次读取、搜索、下载和导出均重新校验对象权限；接口不暴露对象存储真实路径。

规范路径均在/api/v1下：POST /uploads → PUT /uploads/{id}/parts/{n} → POST /uploads/{id}/complete → POST /analysis/tasks → GET /analysis/tasks/{id} → GET /analysis/tasks/{id}/evidence → POST /reviews → POST /reports。取消、重算、风险和取证使用/analysis/tasks/{id}/cancel、/rerun、/risk-findings、/forensics；任务卡可省略共同/api/v1前缀，不能另用/tasks代表同一资源。

### 8.5.1 契约与时间坐标

【建议】幂等作用域、有效期、相同请求摘要和冲突错误写入OpenAPI；排序前施加授权过滤。要求逐请求权限撤销的媒体/证据下载经受控代理重新鉴权，代理外对象存储不直接对浏览器开放。普通预签名URL只有期限/签名身份权限语义，不能自动实现案件授权即时撤销；选择直接签名访问须记录残留窗口与存储策略并验证。回调地址按批准域名与出口策略控制。

业务时间保存UTC及原始时间文本、时区、来源和可信度；首次发现时间不替代发布时间。视频定位统一毫秒和明确的半开区间，保留源PTS/time_base、变帧率及转码回映射。图像框与掩码声明原始尺寸及坐标规则，预处理后逆映射；空音轨、无EXIF和缺失平台时间显式记录未知。

错误按鉴权、输入、状态冲突、容量、依赖和内部故障分类；常用HTTP状态403/404按防泄漏策略、409冲突、413大小、415格式、429限流、503依赖不可用。外部错误不泄露真实文件路径、账号或堆栈，内部以request_id诊断。兼容变更支持旧版本过渡，破坏性变更需新的接口或明确迁移方案。

### 8.5.2 接口契约与标识实现细则

官方机制：OpenAPI 3.1.0定义接口、Schema及安全要求；同一security对象内多种方案需同时满足，数组内对象是可选分支。UUIDv7含毫秒时间戳，RFC明确UUID不能被当作安全能力凭证。[R01—R02]

【建议】shared-contracts维护单一OpenAPI与Schema源。每项接口记录operationId、输入/输出、错误码、认证与对象权限、版本及样例；校验生成代码和文档兼容。明确审查security: []或空对象的匿名例外；API声明不能替代代码中的RBAC/ABAC和资产授权。

POST /uploads只创建上传会话；合并、校验通过后登记asset_id；POST /analysis/tasks只接受可访问且有效资产，校验后返回202、task_id和进度查询地址。Idempotency-Key绑定调用人、操作和规范化请求摘要；相同键且摘要不一致返回冲突，相同键返回原任务。有效期与保存策略经评审，不能因清理键而重复生成业务效果。

### 8.5.3 媒体时间轴与坐标实现细则

官方机制：ffprobe支持流、帧及容器元数据输出；FFmpeg AVFrame的显示时间戳按相应时基表达。[R06—R07]

【建议】保存stream_index、PTS、time_base、起点、可变帧率及缺失时间戳标记；以PTS和时基换算显示时间，不能一律用帧号÷平均帧率。业务时间相对原件播放起点；倒放、变速、抽帧、补帧及重编码副本另保存mapping_version和映射表。缺失PTS采用记录了来源的估算并保留不确定性，不伪造为原始测量。

区域记录原件尺寸、方向校正、裁剪和缩放/填充变换，掩码和框从模型坐标回映射原件。时间区间统一[start_ms,end_ms)，校验范围与顺序；媒体时长和PTS舍入规则在契约中声明。T042/T050/T087—T089验证VFR、非零起点、旋转、缺失PTS、变速及倒放。

### 8.8 容量与恢复设计

【建议】容量输入包括日文件数D、平均大小S、保留天数R、派生占比α、冗余β；对象容量Cobj=D×S×R×(1+α)×β。不同对象保留不同则分别计算，备份、临时处理、版本迁移和增长空间另计，不能重复乘冗余又重复计副本。视频帧日增量F=Dv×Tv×rf。

向量容量按每种能力分别计N×dim×每维字节，另计索引、元数据、加载集合、副本、重建与切换峰值。2000万×512×4=40.96 GB约38.15 GiB为单路裸向量；两路同规模约76.29 GiB，两路双版本均驻留约152.59 GiB，已超过本机整机内存。该条件例不代表实际采用方案；2000万若为多路总数不得每路重复计算。量化、mmap/磁盘索引须测召回/时延折中，不能只按裸向量保证装得下。

任务容量按混合比例、素材时长/分辨率、CPU解码、模型吞吐、队列、IO和网络测量，同时记录在途与运行任务、等待时延、端到端P50/P95/P99、成功率和处理速率。无GPU的模拟结果只能验证编排，不能证明正式算法并发。

备份清单覆盖SQL事务数据、原件与证据对象版本、授权与审批、配置、模型和必要索引元数据。指定备份域、加密、访问角色、频率、保留、完整性和恢复顺序；在隔离恢复环境验证权限、对象引用和证据哈希。RPO/RTO、备份目标、业务保留及停机窗口通过Q-31确认，任务节点恢复不能代替系统备份恢复。

### 8.9 授权向量检索与索引可见性

官方机制：Milvus支持按标量条件限定检索范围，并提供不同一致性级别；默认或较弱一致性不能代替业务的即时授权撤销要求。[R08—R09]

【建议】服务端从当前权限生成tenant_id、case_id、authorization_status过滤条件，限制召回范围并对asset_id作权威复核。权限变化拒绝新查询与受控下载请求；异步索引清理不能留下可访问旧结果。签名凭据、缓存、Range与在途下载边界见§8.14；过滤字段和短TTL均不替代对象授权。

模型及预处理版本、向量维数、距离度量、归一化、索引参数与集合版本一同登记。新索引先构建、校验数量和可见性、抽查召回及权限，再切换别名；保留回滚版并避免新旧向量混搜。强/会话等读策略按刚写入可见性需求选择并实测。索引性能与Recall使用相同过滤负载评测，T081/T082/T157负责闭环。

### 8.10 对象版本与证据保留实现细则

官方机制：S3 Object Lock依赖版本控制，保护具体对象版本；Governance和Compliance模式的可绕过权限及保留规则不同。MinIO旧文档地址现转至AIStor，其许可、版本和能力须针对实际候选核验。[R10—R11]

【建议】EvidenceManifest绑定bucket、object_key、version_id、SHA-256、来源asset_id、result_version、采集与固化时间、签名及保留策略版本。ETag不通用地等于SHA-256。读文件前校验授权，核对锁定版本和摘要；新上传同名对象不覆盖引用版本。保留模式、期间、legal hold授权及到期处理由安全/业务负责人批准。

先用非敏感样例验证实际对象存储的锁定、删除、覆盖、治理绕过、保留变更、恢复和时钟异常。采用其他S3兼容实现时必须单独做兼容PoC；不因API兼容就认定具备相同不可变保证，也不因加锁/签名就认定司法证据效力。T025/T104/T105/T121提供记录；当前不修改真实保留策略。

### 8.11 容器资源与可观测性实现细则

官方机制：Docker容器默认不设置资源限制；OpenTelemetry通过trace/span上下文及异步链接连接跨服务执行。[R12、R20]

【建议】按§8.7现场快照制定项目配额，明确容器CPU/内存/进程数、临时盘、解码并行与上传/队列上限，预留宿主及其他项目余量。核对实际cgroup生效参数及OOM行为；仅写Compose配置不代表已生效。当前未确认GPU，不配置虚假CUDA设备或把宿主全量内存当项目独占配额。

在API、投递、节点执行、网关和报告环节传播trace_id，另绑定task_id、run_version及attempt；指标包含排队、解码、推理、审核等待、失败、重试和资源占用。trace不能替代审计记录；不把令牌、媒体原件、案件原文或高基数资产ID写入公开指标标签，采样日志也不能充当全量证据台账。T004/T008/T055/T120验证。

### 8.12 数据库与跨存储恢复实现细则

官方机制：PostgreSQL PITR依靠基础备份与连续WAL，pg_dump/pg_dumpall逻辑导出不是其基础备份；配置文件需另行备份。[R19]

【建议】按批准RPO/RTO选择逻辑恢复或PITR方案，记录备份清单、WAL连续性、密钥恢复、监控和隔离恢复目标。SQL、对象版本、模型、索引清单和批准记录通过恢复批次与摘要关联；恢复后对缺对象、孤立引用、权限与授权、报告绑定和证据摘要执行对账，再开放服务。索引可重建部分与必须保留原件分别列出。

T121演练备份损坏、WAL缺段、数据库恢复点与对象版本不一致、索引重建和凭据缺失。另测实际恢复时间及丢失窗口；任务断点重试、单机多容器、同盘复制均不能代替独立恢复与故障域安排。备份目的地及保留政策仍按Q-31确认。

### 8.14 接口真源与下载授权撤销

shared-contracts维护单一OpenAPI/Schema，全部任务接口采用/api/v1/analysis/tasks及其子资源；upload/asset/task标识和error模型分别定义。记录operationId、权限、幂等、版本和样例，生成前端客户端与服务校验。历史/tasks别名如保留，必须有兼容与弃用记录，不能产生第二套契约。

要求逐请求权限检查的媒体播放/证据下载经受控代理，凭据绑定主体、对象version_id、用途、期限及撤销版本；对象存储只对服务身份开放。普通S3预签名URL是持有者凭据，应用授权变更不会自动使它失效（R37）。直接签名路线须证明存储权限映射及残留窗口，否则不能承诺即时撤销。

撤销后拒绝新的下载/Range请求并刷新缓存授权；在途流按明确检查点中止或声明截止边界，已下载字节无法收回。测试覆盖先获凭据再撤销、换账号/案件、续传/重放、旧版本及缓存，不能仅测撤销后新申请。

### 9.6 安全验证与供应链

【建议】上传按白名单解析真实格式并限制大小、时长、分辨率、解压量及处理耗时；查毒失败或不可用时隔离待处理。媒体处理以低权限、无不必要网络、限制资源的工作节点执行，不能仅凭扩展名或上传成功视为安全。URL采集、回调及重定向需限定协议、域名与解析后的地址，防止SSRF；已批准内网地址按明确清单放行。

权限测试覆盖单位、案件、对象、搜索候选、统计、证据下载、SSE订阅和导出；权限撤销后会话和缓存不得继续泄露数据。密钥不入仓库和日志，服务身份最小权限、轮换及审计。提示注入、恶意证据、工具越权和无证据生成纳入回归，大模型不能调用删除、发布或导出能力。

镜像、软件、模型、权重和数据集登记来源、许可、摘要及SBOM；导入扫描、离线包、签名校验、缺陷处置和补丁升级形成可追踪记录。签名算法及可信时间服务按适用密码和取证要求确定，SHA-256只用于本稿内容完整性设计，不能单凭哈希宣称证据真实或具有法律效力。

严重或高危缺陷未修复时原则上不发布；是否允许风险接受由有权责任方确认并记录条件及期限，不能由开发人员自行豁免。告警覆盖任务积压、失败、索引版本错配、磁盘/内存不足和证据校验异常；事件处置保全记录、控制影响、恢复并复盘。

### 9.7 不可信媒体与外部内容安全细则

官方机制：OWASP建议多层上传验证、存储隔离和大小限制；SSRF防御包括出站目标验证与重定向控制；提示注入防御应在模型外执行工具参数和调用权限校验。[R13—R15]

【建议】先进入隔离区，以允许扩展名、签名/容器探测、大小/时长/分辨率、查毒及解析预算共同判断，不信任客户端MIME。非特权解码容器禁出站、限制协议与CPU/内存/进程/临时盘；损坏媒体和查毒不可用不直接发布可分析资产。格式标准化仅生成派生副本，保留原件。

URL接入仅走获准适配器，限制scheme/host/port，核对解析出的IPv4/IPv6，阻断回环、链路本地和未授权内网/元数据目标。内网对接用单独批准白名单；默认不跟随重定向，必要跳转逐跳验证，防DNS重绑定并约束出站网络。不得将用户URL直接交给ffprobe解码。

OCR、ASR、网页与检索证据均为不可信数据，不作为工具指令。模型默认无发布、下载授权、审批或数据库写权；参数、数据范围及副作用在工具实现外层验证。模型文本经Schema、句级支持、敏感信息和安全渲染检查，注入或缺证据转人工。过滤器命中率不等于完全防御效果，T118/T119使用构造样例测试直接与间接注入。

三段式冻结规则

【建议】区分候选版本、评审提交版本和验收发布版本。候选允许继续修订，但保存版本差异；评审期间不得静默覆盖；验收发布版本不可就地修改，变更形成新版本并复测。

| 冻结阶段 | 含义 | 允许的变更 | 适用对象 |
| --- | --- | --- | --- |
| 候选冻结（ Candidate Freeze ） | 内容已成文但未经批准，工程可按此 预研 | 可自由修订，须记版本号 | 架构决策候选、选型候选、排期建议 |
| 交付冻结（ Delivery Freeze ） | 已提交评审 / 交付，评审期间 不得静默修改 | 仅可通过变更记录修改，需评审确认 | 本方案、开发输入材料、技术基线 |
| 发布冻结（ Release Freeze ） | 已用于验收 / 生产， 只读 | 任何修改须走变更流程并重新验收 | 冻结数据集、发布基线、验收版本 |


三条冻结纪律：

候选不等于交付：所有带【建议】标记的内容处于候选冻结状态，不得在评审材料中当作已批准结论引用。

交付冻结须留痕：交付冻结后的任何修订，必须在修订记录中登记"修改前后值、修改依据、批准角色"，并在方案正文保留修订历史。

发布冻结不可逆：进入发布冻结的对象不得就地修改；如需变更，须产生新版本并重新走验收，旧版本保留可追溯。
